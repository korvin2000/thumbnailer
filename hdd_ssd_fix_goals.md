## Проблема

Чтение рассчитано на SSD: параллельность выбрана по CPU, а не по диску.

- Скан: до `index-threads` (= ядра) альбомов в работе, по виртуальному потоку на альбом; каждый сам листает папку/архив
  и читает головы (128 КиБ) новых изображений — N независимых потоков чтения, на HDD головка прыгает между N папками
  на каждом файле. `index-threads=1` убирает прыжки, но диск простаивает, пока CPU декодирует обложку.
- Корни сканируются строго по очереди (`ScanService.scan`, цикл по scopes): два диска никогда не читаются параллельно.
- Просмотр альбома: миниатюра на запрос, браузер шлёт ≤ 6 запросов (HTTP/1.1), каждый читает файл целиком; на HDD
  6 больших чтений чередуются. Устаревшие запросы браузер отменяет сам, на сервер приходит ≤ 6 — LIFO не нужен.
- Solid 7z и tar внутри gz/bz2/xz: миниатюра записи k = распаковка с начала блока до k (`SevenZipContainer.extract`,
  контейнер открывается на каждый запрос), галерея из N снимков = Θ(N²) распаковки — на любом носителе.
- Скан solid-архива с PNG/GIF/BMP/TIFF: `ImageProbe.probe(head)` понимает только JPEG и WebP, остальные уходят в
  `later` → `probe(container, name)` → полное извлечение каждого файла с начала блока — тоже Θ(N²); в папке — второе
  чтение каждого такого файла.
- Windows: `DirectoryContainer.items()` делает `GetFileAttributesEx` на каждый файл (`Files.readAttributes` кэш не
  использует; проверено по исходникам JDK 27), хотя `FindNextFile` уже отдал размер и mtime; на холодном HDD это
  чтения записей MFT при каждом пересканировании.

## Цели

- HDD: чтение близко к последовательному, CPU-работа перекрыта с чтением; разные диски читаются параллельно.
- SSD: без регрессии против текущего поведения (ни по скорости, ни по памяти).
- Тип носителя определяется сам; сеть, WebDAV, облачные и неопределённые диски — как HDD; ручное переопределение на корень.
- Просмотр галереи (папка, zip, rar, 7z, tar) быстрый на обоих типах; solid-архивы — один проход вместо Θ(N²).
- Память ограничена при любом размере библиотеки и архива.
- Инварианты не меняются: библиотека read-only, `AlbumService` — единственный писатель, миниатюры записей не хранятся,
  отмена, прерывание и `close()` работают, удаление альбомов только после полного обхода.
- Выигрыш измерен на холодном кэше, а не предположен.

## Решение: дорожка (Lane) на диск вместо читателя с очередью

**Lane** — право читать с физического диска. HDD (и сеть/неизвестное): справедливый `Semaphore(n, true)`, FIFO,
`n = thumbnailer.hdd-readers` (по умолчанию 1; замерить 1 и 2 — при одном запросе в очереди NCQ не сортирует
seek'и); SSD: без ограничения (как сейчас). На диск две дорожки, `scan` и `view`: просмотр не стоит в очереди скана.
Скан уступает просмотру: на HDD дорожка скана ждёт, пока дорожка просмотра того же диска не простоит `QUIET`
(300 мс), — перед ходом альбома и между чтениями голов (`Lane.giveWay`).

Правила (deadlock-free: граф ожиданий ацикличен):
- Порядок захвата везде **lane (ход диска) → место в очереди → слот декодера**, никогда наоборот; никто не ждёт
  того, что берётся раньше.
- Lane не реентерабельна и не удерживается через вызов, который берёт её снова; захват прерываемый; после захвата —
  проверка `cancelled`; освобождение только в `finally`; `Hold.close` идемпотентен, ход можно передать. Мёртвая
  сетевая шара блокирует дорожку своего диска (`RandomAccessFile`/`ZipFile` не прерываются) — лог долгих удержаний
  открыт.
- `Limiter` справедливый (`super(0, true)`): ожидающего с ходом диска никто не обгоняет.

**Конвейер «последовательное чтение → параллельная обработка»** (`AlbumService.render`, требование владельца):
ход диска (FIFO, один читатель на HDD) → место в очереди (`coverQueue`/`thumbQueue`, 2 × threads прочитанных файлов)
→ `container.read` → **ход отпущен** → слот декодера (`coverSlots`/`thumbSlots`, threads) → decode, resize, encode
в WebP/JPEG. Диск наполняет очередь строго по одному, а масштабирование и кодирование идут параллельно в до
`threads` потоках; полная очередь придерживает читателя, так что память ограничена (≤ 2 × threads файлов).
Вместо отдельного пула воркеров «задание» несёт свой виртуальный поток: тот же FIFO, без проброса отмены и ошибок.

**Скан, альбом** (`Reconciler` + `AlbumIndexer`): `scan`-ход от открытия контейнера до прочтения первой обложки:
подпись, листинг, головы, поздние пробы, `metadata.extract`, затем место в очереди и `container.read` кандидата →
**ход отпущен** → слот → decode/resize/encode → commit. Хранимая обложка (без чтения) — ход отпускается после
`metadata.extract`. Нерабочий кандидат: следующий ждёт новый ход. Один проход очереди на альбом, обложка читается
рядом с головами; пока альбом декодирует, диск читает следующий. Проход solid-архива — один поток под lane
(распаковка на одном ядре; на библиотеке из solid-архивов сравнить `hdd-readers` 1 и 2).

**HTTP** (промах обложки, миниатюра записи из папки/zip/non-solid): `view`-ход → очередь → read → ход отпущен → слот
→ decode; 6 запросов браузера читаются по одному и декодируются параллельно.

**Галерейный проход** (solid 7z, обёрнутый tar; `AlbumContainer.sequential()`): один `GalleryPass` на (album id,
revision, epoch миниатюр) в `AlbumService`, на своём виртуальном потоке — он владелец 7-Zip-прохода, прерывание =
отмена. Темп по спросу: распаковывает до `maxDemanded + lookahead` (~24), затем паркуется в sink и на паузе отпускает
`view`-lane. Sink копирует запись в нативную память (shared arena, не heap), рендер под `thumbSlots` с ожиданием,
чувствительным к отмене (поток 7-Zip не получает interrupt владельца). Готовые миниатюры — в карте «выдал и забыл»
(браузер кэширует по revision), поэтому память = lookahead × ~40 КБ. HTTP-запрос только ждёт future, lane и slot не
держит. Битая/пропущенная запись — future с ошибкой по концу прохода; запрос назад от уже забытого — перезапуск;
простой ~60 с — закрытие; глобально ≤ 2 прохода. Обёрнутый tar = проход листинга + проход рендера (линейно).

**Solid-архивы — строго последовательно** (требование владельца): распаковка записи зависит от всех предыдущих в блоке,
поэтому любое обращение к нескольким файлам solid 7z/RAR или обёрнутого tar — один проход в порядке упаковки (индекс
записи), никогда не цикл извлечений по имени. Скан: головы — один проход (уже так), остальные пробы и метаданные
берутся из того же прохода (головы распознаваемых из начала форматов, сохранённые головы остальных); обложка — один
частичный проход до её записи; просмотр — `GalleryPass` в порядке упаковки. Доступ к одной записи (оригинал в
lightbox) — неизбежно частичный проход от начала блока.

**Почему не читатель + FIFO + CPU-воркеры** (исходные идеи 1–3, 7): lane даёт то же расписание диска (FIFO ≈ порядок
обхода, один поток), перекрытие I/O и CPU — бесплатно от остальных виртуальных потоков в полёте. Не нужны поток-
читатель, очередь с лимитом в байтах, правило крупного элемента, отдельный пул CPU, проброс отмены и ошибок между
стадиями. Ёмкость очереди — в штуках (2 × threads), а не 256 МБ: память ограничена тем же порядком, что и раньше.

## Ответы на открытые вопросы

- **Корень → диск**: Windows — номер устройства тома; составной том (Storage Spaces, динамический, RAID, VHD) не
  отвечает или отвечает за виртуальный диск → ключ = том, тип по штрафу seek или hdd. Linux — whole-disk/dm из sysfs
  (btrfs на нескольких устройствах — по устройству монтирования). Сеть — ключ = сервер/шара. Тома, смонтированные
  внутри корня, наследуют вердикт корня (редко; переопределение `storage` по корню).
- **Читатели для SSD**: ноль — lane пустая; на SSD конвейер ничего не даёт, CPU и так ограничен `coverSlots`.
- **Сеть/NAS**: hdd (решение владельца). На каналах с большой задержкой один поток упирается в RTT — `storage: ssd`.
- **Solid 7z, обёрнутый tar**: при скане проход целиком внутри фазы альбома под lane; при просмотре — `GalleryPass`.
- **Порядок MFT/данные**: обход и индексация уже чередуются по альбомам (обход ждёт слот), отдельная фаза «сначала
  весь обход» не нужна и стоила бы памяти, пропорциональной библиотеке.
- **Замер**: строка лога `Scanned …: N albums, M changed in T ms`; просмотр — время заполнения экрана миниатюр
  (DevTools Network); холодный кэш — см. «Стенды».

   машине сборки не падает, неизвестное → hdd; C: → ssd, V: → hdd (D: — только в финальном тесте).
2. **Скан под lane**: Reconciler/AlbumIndexer/AlbumService/Thumbnailer/Limiter; `ScanTest` зелёный.
3. **Дешёвые выигрыши**: пробы PNG/GIF/BMP/TIFF из головы, `walkFileTree` в `DirectoryContainer`, физический порядок
   голов (тест: zip с центральным каталогом не по имени).
4. **GalleryPass** (тест: solid 7z из `Archives` — все миниатюры одним проходом, отмена, битая запись).
5. **Параллельные корни** на разных дисках — после замера п. 2 (C: + V: одновременно).
6. **Финальный замер**: холодный D: (зарезервирован), C:, V:; `hdd-readers` 1 vs 2; просмотр папки и 7z-альбома.
   Ревью кода Codex **gpt-6.1-sol, xhigh** (read-only); исправить находки.
7. **Документация** в том же изменении: карты, SPEC (S6 + строка о носителе и галерее), ARCHITECTURE §2/§3,
   README/CLAUDE (`storage`, `hdd-readers`, `index-threads`), backend/CLAUDE.md Threads (lane → Limiter, `GalleryPass`),
   PLAN (Decisions: lane вместо очереди).

## Отклонено из исходной версии

- Читатель на диск + FIFO с лимитом в байтах + CPU-воркеры + правило крупного элемента — заменены lane.
- «Несправедливый Semaphore ломает порядок» — неверно для `Semaphore(n, true)` с удержанием на всю фазу альбома.
- «Читатель на физический диск» без параллельного обхода корней ничего не даёт — добавлен п. 5.
- Миниатюры в UI «вне рамок» — включены: `view`-lane, уступка скана, `GalleryPass`; LIFO/отмена на сервере не нужны.
- Сортировка zip по смещениям локальных заголовков — у `ZipFile` нет API; порядок центрального каталога — эвристика.
- Отдельный шаг «сначала вручную, потом автоопределение» — один шаг: автоопределение и есть продукт.
- Таймерное определение типа (Fable) — зависит от кэша; «apfs → ssd» — неверно.
